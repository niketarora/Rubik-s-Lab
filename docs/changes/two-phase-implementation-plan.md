# Two-Phase (Kociemba) Solver — Implementation Plan

## 0. Status Before Starting

This is **not a greenfield feature**. Per `context.md` §9 and §41:

- `solver-engine/include/algorithms/TwoPhase.hpp` already exists.
- `main.cpp` already references Two-Phase code.
- `CMakeLists.txt` does **not** currently include `src/algorithms/TwoPhase.cpp` in the build.
- Public product positioning (§9) currently advertises only BFS/DFS/IDDFS/IDA*.

So before writing a single line of new code, this plan starts with an **audit phase**, not an implementation phase. Do not assume the existing `TwoPhase.hpp`/`.cpp` is empty, correct, complete, or safe to build as-is. Do not assume it is garbage either. Find out.

This plan also respects §62 (Absolute Priorities): Correctness > Verified solutions > Consistent state representation > Real API integration > Real metrics > Reproducible benchmarks > Security > UX polish > New features. Two-Phase is a **new feature** relative to the current MVP. If Priorities 1–5 from §59 (cube correctness, real solver CLI, CMake completeness, backend contract, real solve flow) are not yet done for the existing four algorithms, that work should land first or in parallel — not be displaced by this. This plan assumes Two-Phase is built as a fifth, clearly-labeled, additive mode once (or alongside) that stabilization, not a substitute for it.

## 1. Phase A — Audit (do this first, no code changes)

Goal: establish ground truth so we never "silently pretend" docs and code agree (per §0).

   - What coordinates/tables it assumes exist.
   - What it expects from `Cube.hpp` / `CompactCube` / `PieceCube`.
   - What's declared vs. actually defined (header-only stub vs. real logic).
2. Check for `solver-engine/src/algorithms/TwoPhase.cpp`. If present, read it. If absent, the header is declaration-only and there is no implementation to reuse — treat as design sketch only.
3. Grep `main.cpp` for every Two-Phase reference: which `SolveOptions.algorithm` enum value routes to it, what it passes in, what it expects back.
4. Attempt a manual compile that includes `TwoPhase.cpp` explicitly (the way §41 says someone already did once) and record every compiler error. This tells us how far from working it actually is.
5. Check `solver-engine/include/heuristics/Heuristics.hpp` and `solver-engine/include/algorithms/Search.hpp` for any coordinate/pruning-table scaffolding that Two-Phase might already share.
6. Produce a short **Audit Findings** note (checked into `docs/algorithms/two-phase-audit.md`, not this plan) with one of three conclusions:
   - **(a) Salvageable** — fix/complete the existing skeleton.

   - **(c) Not salvageable** — remove/replace, document why in `docs/changes/changes-v1.md`.

Do not proceed to Phase B until this note exists. This is the "identify any contract/schema/state mismatch" and "when documentation and code disagree, explicitly identify the discrepancy" steps from §64, applied to code-vs-code (header vs. CMake vs. main.cpp) rather than doc-vs-code.

## 2. Design Decisions to Lock Before Coding

These need explicit answers up front so the algorithm doesn't quietly redefine shared contracts (§64 rule 10: "Never silently change the cube-state contract").

| Decision | Options | Recommendation |
|---|---|---|
| Where do coordinate conversions live? | (a) inside `TwoPhase.cpp` only, (b) a new `CoordinateCube` type shared under `cube/` | (b) — keeps `Cube.hpp` canonical; Two-Phase gets a private derived view, not a fork of cube logic |
| Table generation timing | (a) at solver process startup every run, (b) generated once and cached to disk, loaded at startup | (b) for production; (a) acceptable for first working version to avoid file I/O complexity, revisit after correctness is proven |
| Where are cached tables stored | e.g. `solver-engine/data/tables/*.bin` | new `data/` dir, gitignored, generated by a build step or first run |
| New `SolveOptions.algorithm` enum value | `"TWO_PHASE"` | matches existing string-enum style (`IDA_STAR`, etc. per §18 example) |
| Metrics shape | reuse existing `nodesGenerated/nodesExpanded/...` fields, add phase-specific fields | extend metrics object with `phase1Length`, `phase2Length`, `phase1Nodes`, `phase2Nodes`, `tableBuildMs`, `tableSource` (`"generated"` / `"cached"`) rather than overloading existing fields with different meaning |
| Move set exposed to user | still all 18 STHM moves in the *solution output* | Two-Phase only *searches* in restricted move sets internally; the emitted solution must be validated the same way as any other algorithm (§17) |
| Positioning to the user | new algorithm option, not a replacement | label clearly, e.g. `"Kociemba Two-Phase (near-optimal, fast)"`, distinct from the four DSA-teaching algorithms so nobody mistakes it for "IDA* but better" |

Flag any of these that conflicts with an existing `docs/trd/rubiks-cube-trd-v2.md` decision before proceeding — TRD is a source of truth per §0.

## 3. Coordinate System (what Phase B actually builds)

Standard Kociemba coordinates, all derived from the existing `PieceCube`/`CompactCube`:

- `cornerOrientation` — 0..2186 (3^7, last corner determined)
- `edgeOrientation` — 0..2047 (2^11, last edge determined)
- `udSliceEdges` — 0..494 (C(12,4), which 4 edges occupy the UD-slice, order ignored)
- `cornerPermutation` — 0..40319 (8!)
- `edgePermutation` (non-slice, 8 edges) — 0..40319 (8!)
- `udSliceSorted` — 0..11879 (12P4, ordered slice-edge permutation, phase 2 only)

Phase 1 goal (subgroup **G1**): `cornerOrientation == 0 && edgeOrientation == 0 && udSliceEdges == 0` (using solved-state indexing convention).

Phase 2 goal: solved state, searched only over `{U, D, L2, R2, F2, B2}` — note: **not** just the 6 half-turns of side faces; U/D remain full-turn since they don't disturb the slice once in G1. (Confirm this against whichever reference is used in step 4 below — don't hand-wave it into code from memory.)

## 4. Reference Correctness Strategy

Kociemba's algorithm has well-known, easy-to-get-subtly-wrong details (coordinate move-table generation, parity handling, phase-2 move restriction). Plan for this explicitly rather than debugging blind:

1. Before writing search code, write **table-generation unit tests** with known small facts (e.g., number of reachable states in G1 from solved = 1; a single quarter turn moves `cornerOrientation`/`edgeOrientation` by known deltas that can be hand-verified for at least a couple of moves).
2. Validate against **published state counts**: |G1| = 2,217,093,120 (in the raw, non-symmetry-reduced formulation this project will use for a first version — no symmetry reduction planned initially, see §7 "Explicitly Out of Scope"). Cross-check pruning table population counts sum to expected totals.
3. Cross-check output solutions against an independent reference implementation's output for a fixed small set of scrambles (e.g. run the well-known `kociemba` Python/JS package or `min2phase` offline, only as an oracle for comparison — not linked into the product). Never claim "matches Kociemba" without this check (§64 rule 8: never fake solver results).

## 5. Implementation Steps (Phase B)

Ordered so each step is independently testable before the next begins.

### Step 1 — `CoordinateCube` conversion layer
- New file(s): `solver-engine/include/cube/CoordinateCube.hpp`, `solver-engine/src/cube/CoordinateCube.cpp`.
- Pure functions: `PieceCube → CoordinateCube` and back (back-conversion only needed for tests/debugging, not the hot path).
- Unit tests: solved cube → all coordinates 0; each of the 18 moves applied to solved cube produces expected coordinate deltas (hand-computed or oracle-checked for at least U, R, F).

### Step 2 — Move tables
- For each of the 6 relevant coordinates, precompute `coordinate × move → coordinate`.
- Store as `std::vector<std::array<uint16_t,18>>` (phase 1 coords) / `<uint16_t,6>` (phase 2 restricted coords).
- Unit test: applying a move then its inverse via the table returns original coordinate, for a sample of states.

### Step 3 — Pruning tables
- Backward BFS from goal coordinate combos (see §3), storing minimum move count in `std::vector<uint8_t>` (values 0–~12 easily fit in a byte; use 0xFF/sentinel for "unvisited").
- For phase 1: combine `cornerOrientation` and `edgeOrientation+udSliceEdges` (or similar split — decide during design, this is the standard two-table combination in reference implementations) to bound memory.
- For phase 2: combine `cornerPermutation` and `udSliceSorted`-restricted-permutation similarly.
- Unit test: known distances for solved and a handful of small manually-scrambled states; table generation completes and total memory stays within a documented budget (record actual MB in the audit/notes).

### Step 4 — Table caching
- Serialize generated tables to `solver-engine/data/tables/*.bin` with a version header (bump on any coordinate/table format change).
- On startup: if cache file exists and version matches, load; else generate and write cache.
- Unit/integration test: delete cache → first run regenerates and produces same solve results as a run using the cache.

### Step 5 — Phase 1 search
- IDA* over 18 moves, heuristic = phase-1 pruning table lookup, goal = G1 membership.
- Must reuse the existing move-application/search cancellation/timeout conventions used by `IDAStar.hpp` (§13.4 requirements: safe timeout, safe depth limit, cancellation, no false SOLVED).
- Unit tests: solved cube → phase 1 length 0; a handful of scrambles → phase 1 terminates and lands in G1 (verify via coordinate check, not by trusting the search).

### Step 6 — Phase 2 search
- IDA* over the 6 phase-2 moves, heuristic = phase-2 pruning table, goal = fully solved.
- Same cancellation/timeout discipline as Step 5.
- Unit test: feed a known G1 state, confirm phase 2 reaches solved and the combined move sequence, when applied to the original scrambled `PieceCube` via the **existing, already-tested move engine**, reaches solved. This reuses §17's verification requirement — do not add a second, parallel "trust the search" path.

### Step 7 — Two-phase orchestration
- Try multiple phase-1 endpoints (bounded by a time/iteration budget from `SolveOptions`, e.g. `maxDepth`/`timeoutMs` already in the existing contract — do not invent a new unrelated option without wiring it through the full stack per §43) and keep the shortest phase1+phase2 total.
- Emit standard `SolveResult` JSON shape from §18, with the extra metrics fields agreed in §2 above, all in the *existing* JSON envelope — do not create a second response schema.
- Failure paths (`TIMEOUT`, `MEMORY_LIMIT`, `SOLVER_CRASHED`, etc. from §18) must be reachable and tested, not just the happy path.

### Step 8 — Independent verification
- Route Two-Phase output through the exact same "apply solution independently, verify solved" step used for the other four algorithms (§17). No shortcut because "Kociemba is known-correct" — a bug in *this project's* coordinate math is exactly the kind of thing that verification exists to catch.

## 6. Build & Contract Wiring

1. **CMakeLists.txt**: add `src/cube/CoordinateCube.cpp` and `src/algorithms/TwoPhase.cpp` to the source list. Add a build step (or documented manual command, but per §41 "do not leave build behavior dependent on an undocumented manual compiler command") for table cache generation if pre-generation is chosen over first-run generation.
2. **`main.cpp`**: confirm/fix the `algorithm == "TWO_PHASE"` dispatch branch, using whatever `SolveOptions` parsing already exists for the other four.
3. **Backend (`cppSolverService.js`)**: confirm the JSON Lines protocol round-trip is agnostic to which algorithm ran (§19) — if so, no backend code change should be needed beyond schema/enum validation (see Zod schema note below).
4. **Backend request schema**: add `"TWO_PHASE"` to whatever enum/Zod schema validates `algorithm` in `solveRoutes.js`. Do this explicitly — §43 warns that UI controls and backend schema can silently diverge.
5. **Frontend**: add the option to the algorithm selector in `SolverWorkspace.jsx` / `BenchmarkWorkspace.jsx`, gated behind confirmation that the full path (React → Express → C++ → result) works, per §43's "either wire the setting end-to-end or disable/label it as unavailable." Until Steps 1–8 above are done and tested, the frontend should **not** show this option (§64 rule 11: never claim an algorithm is implemented when it's only a UI placeholder).
6. **Docs**: add `docs/algorithms/two-phase.md` following the same structure as the existing `bfs.md`/`dfs.md`/etc. Update `docs/changes/changes-v1.md` with what changed and why. Update §9/§13 of `context.md` itself once this is real, so the doc stops saying "positioning is currently centered on BFS/DFS/IDDFS/IDA*" while being inaccurate.

## 7. Explicitly Out of Scope (for this pass)

To keep this from ballooning past a single reviewable feature:

- Symmetry reduction of pruning tables (the ~48x memory/time reduction real Kociemba implementations use). Note as a documented future optimization, not silently assumed.
- Multi-threaded table generation.
- Exposing Two-Phase-specific tuning knobs (e.g. phase-1 endpoint search budget) in the frontend UI beyond existing `timeoutMs`/`maxDepth`, until there's a real use case and full-stack wiring per §43.
- Using Two-Phase output as a heuristic source for the existing IDA* teaching algorithm (interesting idea, separate feature).
